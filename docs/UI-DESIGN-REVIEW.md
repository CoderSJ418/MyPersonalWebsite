## 二、偏离诊断：4维度深度剖析

### 2.1 需求理解偏差

| 维度       | Portfolio核心需求                       | 实际研究方向                          | 问题判定           |
| ---------- | --------------------------------------- | ------------------------------------- | ------------------ |
| 核心目标   | 90秒内让招聘者判断"这个人值得面试"      | 构建Stripe级视觉系统                  | ❌ **目标替换**     |
| 信息优先级 | 项目经验 > 技术栈 > 个人简介 > 视觉特效 | 视觉特效 > 视觉系统 > 信息呈现        | ❌ **优先级倒置**   |
| 成功标准   | 招聘者快速获取关键信息，发起联系        | CSS变量一致性、光效还原度、竞品对齐度 | ❌ **评价体系错位** |
| 用户画像   | HR/技术面试官，90秒浏览，关注内容       | 设计师同行，审美评判，关注视觉        | ❌ **受众错位**     |

**根因：** 将"Portfolio网站"理解为"展示设计能力的作品"，而非"帮助招聘决策的信息工具"。

[COMPARE]
```
[WRONG] Portfolio = 视觉作品集 → 需要Stripe级光效、4层交互、5大模型
[CORRECT] Portfolio = 招聘决策工具 → 需要信息清晰、加载快速、关键内容突出
```

### 2.2 视觉风格偏移

| 阶段    | 风格定位           | 偏移幅度               | 问题判定       |
| ------- | ------------------ | ---------------------- | -------------- |
| Phase 1 | "修复双风格混合"   | 从bug修复→风格统一     | ⚠️ 合理但过度   |
| Phase 2 | "统一为Aurora风格" | 从风格统一→5大模型建设 | ❌ 工程化过度   |
| Phase 3 | "Stripe级重建"     | 从5大模型→竞品级重建   | ❌ **完全偏移** |

**偏移路径：** 修bug → 统一风格 → 建设视觉系统 → 追逐竞品标准

| 维度 | Portfolio需要的视觉   | Stripe级视觉                                     | 差异                         |
| ---- | --------------------- | ------------------------------------------------ | ---------------------------- |
| 背景 | 干净暗色+微纹理       | 4-6层radial+blur+noise+light field+cursor follow | Portfolio不需要cursor follow |
| 卡片 | 清晰层级+hover反馈    | 4层交互(Depth→Glow→Sweep→Cursor)                 | Portfolio只需1-2层           |
| 动效 | 入场reveal+scroll触发 | 15种特效+stagger+物理曲线                        | Portfolio只需3-5种           |
| 配色 | 1套暗色+1个accent     | 100+CSS变量+3层颜色模型                          | Portfolio需要10-15个变量     |

[COMPARE]
```
[WRONG] "当前Header blur(12px)远不够，Stripe用blur(20px)" — 以Stripe为标准
[CORRECT] "Header blur是否影响招聘者阅读关键信息？" — 以招聘效率为标准
```

### 2.3 交互逻辑冗余

| 交互层级        | 当前实现                             | Portfolio需要                       | 冗余度 |
| --------------- | ------------------------------------ | ----------------------------------- | ------ |
| Layer 0: Depth  | box-shadow 2层                       | ✅ 需要 — 层级感                     | 0%     |
| Layer 1: Glow   | conic-gradient + mask-composite      | ❌ 不需要 — 招聘者不会注意边框发光   | 100%   |
| Layer 2: Sweep  | 105deg linear-gradient 800ms         | ❌ 不需要 — 光扫效果对信息获取无帮助 | 100%   |
| Layer 3: Cursor | radial-gradient 400px + mouse follow | ❌ 不需要 — 鼠标追踪光效是炫技       | 100%   |

| Composable              | 数量 | Portfolio核心需要 | 冗余估计 |
| ----------------------- | ---- | ----------------- | -------- |
| useScrollReveal         | 1    | ✅ 入场动画        | 0%       |
| useMousePosition        | 1    | ❌ 光效追踪        | 100%     |
| useIntersectionObserver | 1    | ✅ 懒加载/触发     | 0%       |
| useTiltEffect           | 1    | ❌ 卡片倾斜        | 100%     |
| useCardInteraction      | 1    | ❌ 4层交互编排     | 80%      |
| 其余25+                 | 25+  | 大部分非核心      | ~70%     |

**量化冗余：** 30+ composables中，Portfolio核心需要约5-8个，冗余率~75%。

### 2.4 功能过度设计

| 设计产出                                        | 规模                | Portfolio需要                         | 问题判定            |
| ----------------------------------------------- | ------------------- | ------------------------------------- | ------------------- |
| 5大模型(Light/Surface/Motion/Hierarchy/Spacing) | 5个完整模型         | 1个简化版Spacing+Color                | ❌ 5→1               |
| 392处旧token迁移                                | 392处变更           | 0 — 从头定义10-15个变量               | ❌ 迁移成本>重建成本 |
| 6条STABILIZATION规则                            | 6条禁止+6条验收     | 不需要 — 如果不过度设计就不需要稳定化 | ❌ 治标不治本        |
| 15个特效拆解                                    | 15个特效+适配度矩阵 | 2-3个入场动效                         | ❌ 15→2              |
| 100+CSS变量(unified-system.css)                 | 100+变量            | 10-15个核心变量                       | ❌ 100→15            |
| 全站6屏逐属性审计                               | 每屏10+属性×6屏     | 每屏3-5个关键属性                     | ❌ 粒度过细          |

**根因公式：**
```
过度设计 = 工程完美主义 × 竞品对标冲动 × 缺少"够用"标准
```

## 三、核心设计目标重定义

### 3.1 Portfolio网站的唯一设计目标

[REQUIRED]
```
所有设计决策必须通过以下检验：
  "这个设计是否让招聘者在90秒内更高效地判断——这个人值得面试？"
  
  是 → 做
  否 → 不做
  不确定 → 不做（直到有证据支持）
```

### 3.2 双模式设计约束

| 模式         | 目标用户  | 时间预算 | 设计要求                               |
| ------------ | --------- | -------- | -------------------------------------- |
| Recruit Mode | HR/面试官 | 90秒     | 信息密度高、层级清晰、CTA突出、加载<2s |
| Reader Mode  | 潜在读者  | 5-30分钟 | 排版舒适、阅读体验好、导航便捷         |

**关键洞察：** Recruit Mode是生存模式，Reader Mode是增值模式。视觉系统必须先服务Recruit Mode。

### 3.3 "足够好"的标准

| 维度        | Stripe级标准                  | Portfolio"足够好"标准            | 差距      |
| ----------- | ----------------------------- | -------------------------------- | --------- |
| 背景        | 4-6层radial+blur+noise+cursor | 暗色基底+1层radial+微noise       | 减少3-4层 |
| 卡片交互    | 4层(Depth+Glow+Sweep+Cursor)  | 2层(Depth+hover反馈)             | 减少2层   |
| 动效        | 15种特效                      | 3种(入场reveal+scroll触发+hover) | 减少12种  |
| CSS变量     | 100+                          | 15个核心变量                     | 减少85+   |
| Composables | 30+                           | 5-8个核心                        | 减少22+   |
| 配色方案    | 3套方案深度对比               | 1套暗色+1个accent                | 直接选1套 |
| 审计粒度    | 每屏10+属性                   | 每屏3-5关键属性                  | 减少一半  |

## 四、纠偏策略

### 4.1 设计决策框架

[REQUIRED]
```
每次设计决策前，必须回答3个问题：

Q1: 这是否直接提升招聘者的信息获取效率？
  → 是：继续
  → 否：跳过

Q2: 去掉这个设计，招聘者是否会误解我的能力？
  → 会：保留
  → 不会：删掉

Q3: 实现这个设计的工程成本，是否低于它带来的招聘效率提升？
  → 是：做
  → 否：简化或跳过
```

### 4.2 视觉系统精简方案

| 当前                   | 精简后                                   | 理由                                           |
| ---------------------- | ---------------------------------------- | ---------------------------------------------- |
| 4层Card交互            | 2层：Depth(hover shadow)+hover位移(-2px) | 招聘者只感知hover反馈，不感知Glow/Sweep/Cursor |
| 4-6层背景radial        | 1-2层radial+blur(60px)                   | 背景是氛围，不是焦点，2层足够                  |
| cursor follow光效      | 删除                                     | 招聘者不会移动鼠标去"发现"光效                 |
| conic-gradient边框发光 | 删除                                     | 边框发光对信息获取零贡献                       |
| 100+CSS变量            | 15个核心变量                             | 见下方变量精简表                               |
| 30+composables         | 5-8个核心                                | 见下方composable精简表                         |
| 15种特效               | 3种：reveal+scroll+hover                 | 其余特效对招聘决策无帮助                       |

[COMPARE]

[CORRECT] 15个核心变量:

### 4.4 Composable精简表

| 保留                    | 用途        | 删除               | 理由                    |
| ----------------------- | ----------- | ------------------ | ----------------------- |
| useScrollReveal         | 入场动画    | useMousePosition   | 光效追踪非核心          |
| useIntersectionObserver | 懒加载/触发 | useTiltEffect      | 卡片倾斜非核心          |
| useTheme                | 主题切换    | useCardInteraction | 4层交互→2层，不需要编排 |
| useReducedMotion        | 无障碍      | useLightSweep      | 光扫非核心              |
| useScrollProgress       | 滚动进度    | useGlowEffect      | 边框发光非核心          |
| —                       | —           | 其余20+            | 按Q1/Q2/Q3检验后删除    |

### 4.5 执行优先级

[REQUIRED]
```
优先级排序（按招聘效率影响）：

P0 — 必须立即做：
  1. 信息层级优化：项目经验/技术栈/联系方式是否90秒可见
  2. 加载性能：首屏<2s，LCP<2.5s
  3. CTA可见性：联系按钮是否在首屏且醒目

P1 — 应该做：
  4. 卡片交互精简：4层→2层，删除Glow/Sweep/Cursor
  5. CSS变量精简：100+→15个核心变量
  6. Composable清理：30+→5-8个核心

P2 — 可以做：
  7. 背景层精简：4-6层→1-2层
  8. 动效精简：15种→3种
  9. unified-system.css重构

[FORBIDDEN] — 不做：
  ✖ Stripe级竞品对照审计
  ✖ 新增任何光效/特效
  ✖ 新增CSS变量（除非替换旧变量）
  ✖ 新增composable（除非替换旧composable）
  ✖ 任何不直接服务招聘效率的设计投入
```

## 五、偏离根因总结

| 根因               | 表现                                                            | 纠偏措施                            |
| ------------------ | --------------------------------------------------------------- | ----------------------------------- |
| **目标替换**       | 从"修bug"升级为"Stripe级重建"，核心目标从招聘效率替换为视觉完美 | 每次决策前过Q1/Q2/Q3检验            |
| **竞品错位**       | 以Stripe/Framer/Raycast为标杆，但它们是产品官网不是Portfolio    | 以"90秒招聘判断"为唯一标杆          |
| **工程洁癖**       | CSS变量5套体系→392处迁移→100+变量，追求系统完整性               | 15个核心变量足够，删繁就简          |
| **缺少"够用"标准** | 没有定义"足够好"的边界，导致无限追求完美                        | 定义P0/P1/P2优先级和[FORBIDDEN]清单 |
| **受众错位**       | 为设计师同行设计，不是为HR/面试官设计                           | Recruit Mode优先，视觉服务于信息    |

## 六、关键教训

[COMPARE]
```
[WRONG] 设计驱动: "Stripe用blur(20px)，我们只有blur(12px)，不够"
[CORRECT] 目标驱动: "招聘者3秒内能否看清项目名称和技术栈？能→够用"

[WRONG] 系统完整性: "CSS变量5套体系不一致，必须统一迁移392处"
[CORRECT] 最小可用: "定义15个核心变量，新组件用新变量，旧组件逐步替换"

[WRONG] 竞品对标: "Framer有mesh gradient，我们也需要4-6层"
[CORRECT] 需求对标: "招聘者需要暗色背景区分层级，1-2层radial足够"

[WRONG] 特效丰富度: "15个特效拆解，适配度矩阵，逐个落地"
[CORRECT] 信息效率: "3种动效(入场+滚动+悬停)覆盖所有招聘场景"
```

### 一句话总结

> **Portfolio的视觉系统是信息的载体，不是展示的对象。**
> 
> 当视觉系统本身成为优化目标时，就已经偏离了Portfolio的核心使命——让招聘者更快地判断"这个人值得面试"。
