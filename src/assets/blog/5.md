> 本文是 2026 年回看 Interop 2024 的工程笔记。它最值得学习的不是某一项 CSS 新特性，而是浏览器厂商如何把“跨浏览器一致性”变成可测量的共同目标。

Interop 项目由主要浏览器厂商与 Web 社区共同推进，每年选择一组跨浏览器差异明显、又会阻碍开发者采用的 Web 能力，通过共享测试提升一致性。2024 年的重点覆盖可访问性、CSS、表单、布局、Popover、滚动条样式和文本换行等领域。

## 兼容性问题为什么经常判断错

常见的错误流程是：看到一个新 API，查到“支持率 90%”，然后直接使用。这个数字没有回答三个关键问题：

1. 你的真实用户是否集中在剩余 10%；
2. 浏览器是完全支持，还是只实现了部分行为；
3. 不支持时，页面是少一点效果，还是核心功能不可用。

兼容决策应该从功能风险开始，而不是从新旧程度开始。

## 建立三层能力模型

### 第一层：核心内容必须可用

导航、表单提交、文章阅读和项目链接不应依赖单一实验能力。即使新 CSS 或 JavaScript API 不可用，用户仍应完成主要任务。

### 第二层：增强效果按能力开启

```css
.project-grid {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(16rem, 1fr));
}

@supports (grid-template-rows: subgrid) {
  .project-card {
    grid-row: span 3;
    grid-template-rows: subgrid;
  }
}
```

基础布局先成立，`subgrid` 只改善卡片内部对齐。能力检测的目标不是“让旧浏览器看起来完全一样”，而是保证信息和操作仍然成立。

### 第三层：装饰性能力可以直接降级

View Transition、模糊、混合模式和指针光效都属于增强层。触摸设备、低性能设备或 reduced-motion 用户可以得到稳定静态版本，不需要用另一套复杂实现追求视觉一致。

## Baseline 应该怎么用

Baseline 帮助判断某项 Web 能力是否已经在主要浏览器中达到可用或广泛可用状态。它适合作为默认判断起点，但不能替代项目自己的浏览器矩阵。

一项能力进入 Baseline 后仍要检查：

- 项目的最低浏览器版本；
- 企业内网、WebView 等特殊环境；
- 无障碍辅助技术组合；
- 是否需要 polyfill，以及 polyfill 体积；
- 降级后是否影响核心任务。

## 什么时候值得使用 polyfill

只有同时满足以下条件时才考虑：

- 功能是核心流程的一部分；
- 目标浏览器确实缺失；
- polyfill 行为足够接近标准；
- 体积与维护成本可接受；
- 无法用更简单的渐进增强处理。

如果只是卡片光效，不加载 polyfill；如果是表单交互或数据解析，才可能值得承担成本。

## 项目里的兼容性记录应该包含什么

```text
能力：Popover API
用途：移动端筛选菜单
最低环境：Chrome / Edge / Safari / Firefox 的项目目标版本
检测方式：'popover' in HTMLElement.prototype
降级：普通定位面板 + 显式关闭按钮
验证：键盘、触摸、Escape、焦点返回
```

相比一句“支持现代浏览器”，这种记录能告诉下一位维护者为什么使用、哪里可能失效、如何验证。

## 发布前检查清单

- 在真实目标浏览器中测试，不只看兼容表；
- 所有交互都有键盘路径和可访问名称；
- reduced-motion 下不启动持续动画；
- 触摸设备不初始化鼠标追踪；
- 关键内容不依赖 `@supports` 内部样式；
- 降级状态与增强状态使用同一份数据；
- 自动化测试覆盖核心行为，不绑定浏览器内部实现。

Interop 2024 留下的长期价值，是让前端兼容从“补丁工作”变成“能力管理”。先定义核心任务，再选择增强能力，页面就不会因为追新特性变得脆弱。
