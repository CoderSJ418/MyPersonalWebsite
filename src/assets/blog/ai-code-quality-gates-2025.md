> 这是一篇 2026 年整理的 2025 年工程方法回顾。AI 编程最容易提升的是产出速度，最容易被忽略的是验证成本；如果没有验收链，生成越快，错误扩散也越快。

“代码已经完成”只是模型对自身输出的描述，不是证据。可靠交付必须由项目外部信号确认：类型检查、测试、构建、浏览器行为、性能数据和人的产品判断。

## 第一步：先给任务分级

不同风险不能使用同一套流程：

```text
P1 新功能 / 架构变化
  需求 → Feature Brief → 方案确认 → 实现 → 全量验证

P2 Bug 修复
  复现 → 根因 → 最小修复 → 定向复测 → 回归

P3 线上阻断
  最小止血 → 验证 → 发布 → 事后文档

P4 文案 / 微调
  修改 → 影响范围验证
```

任务分级的作用不是增加流程，而是避免小改动过度设计、大改动未经确认直接编码。

## 第二步：让约束进入仓库

只在聊天里告诉 AI“注意代码质量”，下一次任务很容易丢失。可执行约束应该放进项目文档和脚本：

- 架构边界与目录职责；
- TypeScript、组件和样式规则；
- 禁止模式及其原因；
- Definition of Done；
- 可重复运行的质量命令；
- 重要决策与例外记录。

好的规则不仅说“禁止”，还说明曾经发生过什么问题，以及正确替代方案是什么。

## 第三步：先复现，再改代码

Bug 修复可以使用固定循环：

1. 用最短路径稳定复现；
2. 缩小到最小组件或函数；
3. 提出一个可以被证伪的根因假设；
4. 增加日志、断言或测试验证假设；
5. 只修改与根因相关的代码；
6. 重复原始复现并执行回归。

如果没有复现证据，AI 很容易修复“看起来可疑”的代码，而不是实际问题。

## 第四步：建立分层质量门禁

### 静态门

```powershell
npm run typecheck
npm run lint:check
```

它们适合发现类型漂移、无效导入和规范问题，但无法证明界面行为正确。

### 行为门

单元测试覆盖纯函数和状态转换；集成测试覆盖组件协作；E2E 覆盖真实用户路径。测试应断言外部行为，不绑定内部类名和动画实现。

### 构建门

```powershell
npm run build
```

构建验证生产编译、路由 chunk 和生成脚本。构建成功仍不代表 SPA 直链、环境变量和部署平台配置正确。

### 运行门

至少检查桌面、移动、触摸、键盘、reduced-motion、无效路由和失败恢复。视觉修改需要真实截图或人工观察，不能只靠 DOM 断言。

## 第五步：保护用户已有改动

AI 进入工作区时要先查看 Git 状态。未知修改默认属于用户：

- 不整体 stage；
- 不使用 `reset --hard`；
- 不为了清理工作区删除陌生文件；
- 新分支保留未提交内容；
- 提交前逐文件检查 diff。

这不是 Git 技巧，而是协作边界。

## 第六步：把产品判断留给人

自动化可以验证按钮可点击、页面无横向滚动、性能分数达标，却不能完全判断文章是否有帮助、视觉是否有说服力、项目是否真实体现个人能力。

人工验收任务应具体：

- 你能否在 10 秒内理解页面用途？
- 修改参数后，预览和代码是否同步？
- 文章是否给出可执行决策，而非术语堆积？
- 移动端操作后，页面是否跳动？
- 这个功能是否值得长期维护？

## AI Review 不能冒充真实用户研究

另一个模型可以发现一致性和技术问题，但它仍然共享相似训练分布，也不会承担真实使用成本。报告应明确标注 AI Proxy Review，并把真实用户研究保留为后续债务。

## 最终完成定义

- 需求与实现一致；
- 没有扩大未授权范围；
- 类型、Lint、测试和构建通过；
- 原始问题复测通过；
- 响应式、无障碍和性能验证通过；
- 文档与代码同步；
- 用户改动被保护；
- 人工确认产品价值；
- 失败项没有通过修改标准被隐藏。

AI 编程真正的能力不是一次生成更多代码，而是持续把不确定输出转化为可验证、可回滚、可维护的工程结果。
