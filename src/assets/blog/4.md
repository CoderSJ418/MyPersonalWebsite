> 本文是 2026 年回看 TypeScript 5.5 与 5.6 的工程笔记。类型系统的价值不是让代码看起来高级，而是把原本会进入运行时的错误提前到编辑器和 CI。

2024 年的 TypeScript 5.5 和 5.6 有几个变化会直接影响日常代码：数组过滤可以推断类型谓词，编译器能识别明显恒真或恒假的条件，内置迭代器的返回类型也更严格。

## 1. 推断类型谓词减少手写断言

过去过滤可空数组后，类型有时仍然包含 `undefined`，开发者常用 `as` 强行绕过：

```ts
const names = users
  .map((user) => user.displayName)
  .filter((name) => name !== undefined)
```

TypeScript 5.5 能为满足条件的回调推断类型谓词，`names` 可以得到 `string[]`。这看似只是少写一段类型守卫，实际意义是减少了“不经验证就断言结果”的习惯。

适合推断的回调通常满足：

- 只有一个明确返回表达式；
- 没有修改参数；
- 返回布尔判断；
- 判断与参数类型的收窄直接相关。

如果业务规则复杂，仍然应该写有名称的类型守卫，让语义可以被测试：

```ts
interface Project {
  id: string
  publishedAt?: string
}

function isPublished(project: Project): project is Project & { publishedAt: string } {
  return typeof project.publishedAt === 'string'
}
```

## 2. 常量条件检查能抓住“看起来像对”的代码

TypeScript 5.6 会报告一些语法上合法、逻辑上几乎肯定错误的条件，例如把正则表达式本身当成判断，或错误组合 `??` 与比较表达式。

```ts
// 忘记调用 test，正则对象永远为真
if (/^lab\//) {
  openRoute()
}

// 正确写法
if (/^lab\//.test(path)) {
  openRoute()
}
```

这种检查的价值在于，它不需要运行测试数据就能发现错误。升级后出现的新报错不要批量关闭；逐条确认它揭示的是代码缺陷、表达式优先级问题，还是确实需要显式注释的特殊逻辑。

## 3. 严格迭代器返回类型堵住一个旧漏洞

生成器或迭代器的 `next()` 结果包含 `value` 与 `done`。当 `done` 为 `true` 时，`value` 的类型可能与正常 yield 值不同。旧类型定义容易把这一部分退化成 `any`，让不安全值继续传播。

开启 `--strictBuiltinIteratorReturn` 后，应先判断完成状态：

```ts
const iterator = new Set(['Vue', 'TypeScript']).values()
const result = iterator.next()

if (!result.done) {
  console.log(result.value.toUpperCase())
}
```

这体现了类型系统的基本原则：一个值是否存在，应由控制流证明，而不是由开发者“知道它应该存在”。

## 4. Vue 项目里最常见的迁移点

### DOM 与模板引用

不要用非空断言掩盖挂载前为空：

```ts
const panel = useTemplateRef<HTMLElement>('panel')

function focusPanel() {
  panel.value?.focus()
}
```

### API 数据

外部响应先当作 `unknown`，经过 schema 或类型守卫验证后再进入 Store。接口类型只描述期望，不能证明网络返回真的符合类型。

### 路由参数

路由参数可能是字符串或字符串数组。应在边界层收窄，不要在多个组件里重复 `as string`。

### catch 变量

错误是 `unknown`。用 `instanceof Error` 或领域错误守卫提取信息，不把任意对象当作 Error。

## 5. 一次安全升级流程

1. 单独创建 TypeScript 升级提交；
2. 同步检查 `vue-tsc`、Vite 与测试工具兼容性；
3. 先运行 `vue-tsc --noEmit` 收集全部新错误；
4. 按“真实缺陷、需要收窄、第三方类型问题”分类；
5. 禁止用批量 `as`、`@ts-ignore` 清空错误；
6. 运行单元测试、构建和关键页面冒烟；
7. 记录新版本解决了哪些风险。

## 判断类型代码是否有价值

可以问三个问题：

- 删除这个断言后，编译器能否自己证明类型？
- 这个类型守卫是否真的检查了运行时数据？
- 类型错误是在领域边界被处理，还是被传到组件深处？

TypeScript 升级不是追版本号。每减少一个没有证据的断言，代码库就少一个“相信我”的隐患。
