> 本文是 2026 年回看 Vite 6 的迁移笔记。版本升级最容易犯的错误，是只验证开发服务器能启动，却没有验证生产构建、插件行为和部署环境。

Vite 6 在 2024 年 11 月发布。它继续保持快速开发体验，同时引入实验性的 Environment API，希望让客户端、SSR、边缘运行时等不同执行环境共享更统一的开发模型。

对普通 Vue SPA 来说，Environment API 当时不是必须采用的新功能。真正有价值的是借升级重新确认构建边界。

## Environment API 在解决什么

传统 Vite 插件经常默认只有两种模式：浏览器客户端与 SSR。实际项目可能还包含 Web Worker、边缘函数、服务端渲染和自定义运行时，它们对模块解析、热更新和构建输出的需求并不相同。

Environment API 尝试把“运行环境”变成明确对象，让插件和框架能够为不同环境配置解析与构建行为。它在 Vite 6 中仍是实验能力，因此判断标准应是：

- 只有框架或基础设施确实管理多运行时时才评估；
- 普通 SPA 不为了使用新 API 引入抽象；
- 插件作者可以提前验证，但要锁定版本并准备迁移；
- 不把实验接口当作长期稳定的业务 API。

## 升级前先列影响面

```text
Node 版本
  ├─ CI 镜像
  ├─ Vercel / 容器运行时
  └─ 团队本地版本

Vite 核心
  ├─ @vitejs/plugin-vue
  ├─ 测试工具
  ├─ 压缩与分析插件
  └─ 自定义插件

产物
  ├─ chunk 拆分
  ├─ CSS 顺序
  ├─ source map
  └─ 静态资源路径
```

这张清单比直接执行 `npm update` 更重要。构建工具问题通常不发生在业务代码，而发生在版本组合和部署差异中。

## 一套可回滚的升级步骤

### 1. 记录升级前基线

至少保留：Node 版本、构建时间、主要 chunk 大小、测试结果和三个关键页面的冒烟截图。没有基线，就无法判断升级带来的是优化还是回归。

### 2. 只升级一组强相关依赖

Vite 与 Vue 插件可以作为一组，TypeScript 与 `vue-tsc` 作为另一组。不要把框架、构建器、测试框架和样式系统放进同一个提交，否则失败后很难定位。

### 3. 检查 Sass 与插件弃用项

Vite 6 默认使用现代 Sass API。依赖旧 API 的配置或插件可能出现警告。警告不是立即失败，但应在继续升级前确认来源，不要把它们永久留在 CI 日志里。

### 4. 验证生产路径

```powershell
npm run typecheck
npm run lint:check
npm run test:run
npm run build
npm run preview
```

随后直接访问动态路由，例如 `/blog/1`，刷新页面确认宿主平台配置了 SPA fallback。开发服务器正常并不能证明正式直链正常。

### 5. 比较构建清单而不是文件名

Vite 升级后哈希和 chunk 名可能变化。自动化检查应断言“目标路由模块存在、预算没有超限”，不要绑定一次构建生成的具体文件名。

## 插件兼容问题如何定位

当构建失败时，先最小化到：Vite、框架插件、一个入口组件。然后逐个恢复插件。每次只验证一个假设：

1. 是 Node 版本不兼容吗？
2. 是插件调用了废弃钩子吗？
3. 是 TypeScript 或 Vue 编译器组合不匹配吗？
4. 是业务代码依赖了开发环境行为吗？

不要通过随机降级多个包“碰”出一个能构建的组合；找到兼容矩阵后把版本原因写进文档。

## 我会保留的升级门禁

- 开发服务器和生产构建都通过；
- 动态路由刷新不返回 404；
- CSS 顺序和关键页面视觉无回归；
- 初始 JavaScript 与最大异步 chunk 不超预算；
- source map、环境变量和日志策略符合生产要求；
- Node 版本在本地、CI 与部署平台一致；
- 能用一个提交回滚。

Vite 6 最值得留下的不是某个配置片段，而是一套升级纪律：先定义边界和证据，再改变工具链。
