> 本文是 2026 年回看 2025 年 Agent 工程变化的笔记。Agent 的核心不是“自动做更多事”，而是让模型在受控状态机里选择下一步，并让每一步都能验证、拒绝和追踪。

2025 年 3 月，OpenAI 发布 Responses API、内置工具和 Agents SDK。相比把多轮消息、工具调用和结果拼接全部写在业务代码里，这套能力提供了更统一的执行与追踪模型。

它降低了编排成本，但没有替应用解决权限、业务校验和高风险操作确认。

## 先区分四个角色

```text
模型：理解意图，提出下一步
工具：执行一个边界清晰的动作
编排器：维护状态、重试、超时和交接
业务系统：权限、数据一致性与最终副作用
```

如果工具直接接受任意命令或任意 URL，模型就绕过了业务边界。好的工具应该像窄接口，而不是远程终端。

## 工具描述就是 API 设计

```ts
interface SearchBlogInput {
  query: string
  category?: 'AI 工程' | 'Vue 工程' | '性能工程'
  limit: number
}

interface SearchBlogResult {
  items: Array<{
    id: string
    title: string
    excerpt: string
  }>
}
```

这个工具只负责搜索博客，不负责删除、发布或修改内容。输入有封闭枚举和数量上限，输出不包含文章正文之外的内部数据。

工具粒度可以用一句话判断：调用失败时，系统能否明确知道哪个动作失败，以及能否安全重试？如果不能，工具通常太大。

## Agent 需要显式状态，而不是无限聊天记录

一个内容审查 Agent 可以有这些状态：

```text
收集文章
  → 检查元数据
  → 检查正文质量
  → 生成修改建议
  → 等待人工批准
  → 应用修改
  → 运行验证
  → 完成 / 回滚
```

每个状态只允许一组工具。等待批准时不能调用写入工具；验证失败后不能直接宣称完成。状态机让失败路径可观察，也限制模型在错误方向上继续扩张动作。

## 哪些动作必须保留人工确认

- 生产部署和合并；
- 删除不可恢复的数据；
- 对外发送消息；
- 产生费用或修改权限；
- 使用用户身份发布内容；
- 无法通过自动检查确认正确性的判断。

确认页面应显示具体动作、目标、影响和可回滚方式，而不是只问“是否允许 Agent 继续”。

## Tracing 不等于记录全部内容

追踪的目的是复盘决策链：哪个 Agent、调用了什么工具、耗时多久、为何失败。它不意味着保存用户原文和所有工具返回。

建议记录：

- workflow 与 schema 版本；
- 工具名称和结果状态；
- 延迟、重试次数和错误类型；
- 人工确认点；
- 最终任务是否达成。

敏感参数应脱敏或不记录。调试便利不能凌驾于隐私边界。

## 失败与恢复必须先设计

工具调用可能超时、返回部分数据或产生已完成一半的副作用。每个工具至少要回答：

1. 是否幂等；
2. 能否重试；
3. 超时后如何确认实际状态；
4. 是否有补偿或回滚动作；
5. 错误应该交给 Agent、用户还是系统处理。

例如部署请求超时后，不应直接再次部署；先查询目标提交是否已经生成部署，再决定下一步。

## 一套最小验收方法

- 正常任务能在限定步数内完成；
- 工具参数不合法时被 Schema 拒绝；
- 无权限动作无法通过换一种说法绕过；
- 工具超时后不会无限重试；
- 人工拒绝后 workflow 正确结束；
- 上下文中出现恶意指令时不改变工具权限；
- 追踪信息足以定位失败，但不泄露敏感内容；
- 最终结果由外部验证确认，不由模型自评。

## 什么时候不需要 Agent

如果流程固定、条件明确、每一步都可以用普通代码表达，状态机或队列通常更可靠。Agent 适合输入开放、路径需要动态选择，但动作边界仍然明确的任务。

好的 Agent 架构不是给模型更多权限，而是把不确定的推理放在确定的执行边界之间。
