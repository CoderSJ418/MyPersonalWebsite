博客审计时发现一篇旧文章正文约 7.1 万字符、包含大量代码块和重复说明。详情页打开后会一次性解析完整 Markdown、执行语法高亮、清理 HTML，再把全部节点放进 DOM。

即使浏览器没有崩溃，这也不是好的阅读体验：用户先面对一堵文字墙，目录过长，移动端很难判断从哪里开始。

## 先拆清四种成本

```text
列表加载：是否为了标题和摘要下载所有正文
网络加载：打开详情时下载多少 Markdown
解析成本：Markdown、高亮和 XSS 清理处理多少内容
DOM 成本：首次向页面插入多少节点
```

优化其中一层，不能宣称解决了全部问题。

## 本项目采用的四层结构

```text
Markdown 文件
  → 构建时生成 blog-meta.json
  → 列表页同步读取轻量元数据
  → 详情页只异步加载目标 Markdown chunk
  → 遇到 fold marker 时先渲染摘要
  → 用户展开后才解析完整正文
```

列表页不会加载正文；详情页只加载当前文章；超长文章首次只解析摘要和前几节。这个结构让普通文章保持直接阅读，长文才使用渐进展开。

## 明确折叠标记，而不是猜长度

```md
## 先读结论

这里是摘要和决策背景。

<!-- article-fold -->

## 完整实现

这里是按需展开的正文。
```

由作者选择折叠点，比组件按字符数截断更可靠。自动截断可能切在代码块、表格或一个重要论证中间，也无法保证预览本身完整。

纯函数只负责拆分原始 Markdown：

```ts
export const ARTICLE_FOLD_MARKER = '<!-- article-fold -->'

export function splitExpandableMarkdown(content: string) {
  const markerIndex = content.indexOf(ARTICLE_FOLD_MARKER)
  if (markerIndex === -1) {
    return { preview: content, full: content, isExpandable: false }
  }

  const preview = content.slice(0, markerIndex).trim()
  const remainder = content.slice(markerIndex + ARTICLE_FOLD_MARKER.length).trim()
  return {
    preview,
    full: `${preview}\n\n${remainder}`,
    isExpandable: remainder.length > 0,
  }
}
```

这个函数可以独立测试，不依赖 Vue 和 DOM。

## 为什么要做独立内容组件

原详情组件同时负责：

- Markdown 异步渲染；
- loading 状态；
- 目录标题提取；
- 长文展开；
- 复制事件；
- 分享、面包屑和相关文章。

继续把折叠逻辑塞进去会让职责失控。因此新增 `BlogArticleContent`，它只处理原始正文到可见正文的状态转换：

```text
props: content, readTime
state: loading, expanded, renderedContent
emits: headingsChange, contentClick
```

详情组件仍负责页面级目录和导航，`BlogMarkdown` 仍负责安全 HTML 排版。组件边界与数据流保持单向。

## 展开时才做什么

初始状态：

1. 找到 fold marker；
2. 提取 preview；
3. 动态加载高亮器；
4. 渲染和清理 preview HTML；
5. 只为 preview 生成目录。

点击展开：

1. 合并 preview 与 remainder；
2. 渲染完整 Markdown；
3. 更新目录；
4. 保留复制事件委托；
5. 按钮变为 `aria-expanded="true"`。

点击收起时要保持控制按钮在视口中的相对位置，否则数万字符从 DOM 消失会让页面突然跳到不可预测的位置。

## 这个方案没有解决什么

打开详情页时，完整 Markdown 文件仍然作为一个异步 chunk 下载。因此它减少的是首次解析与 DOM 成本，不是详情页网络体积。

如果单篇文章继续增长，下一步应把它真正拆成多篇或多个独立章节文件：

```text
/blog/visual-effects-overview
/blog/visual-effects-card
/blog/visual-effects-scroll
/blog/visual-effects-performance
```

这样每篇有独立主题、URL、摘要与搜索入口，比无限增长的“终极大全”更容易维护。

## 为什么不用 CSS `max-height`

```css
.article-preview {
  max-height: 60rem;
  overflow: hidden;
}
```

这只隐藏视觉区域，完整 HTML 仍然已经解析并进入 DOM，语法高亮和 XSS 清理成本也已经发生。它适合简单视觉裁切，不适合解决长文首次渲染问题。

## 内容构建也需要质量门

Markdown 是源码，就应该像代码一样检查：

- frontmatter 必填字段完整；
- 文件名 ID 与元数据唯一；
- 日期有效；
- 标签至少两项；
- 正文达到最低信息量；
- 禁止“内容过长，此处省略”等占位句；
- 年度文章数量满足内容规划；
- 生成后的元数据与 Markdown 同步；
- Sitemap 和 RSS 使用同一索引。

本项目提供两个命令：

```powershell
npm run content:generate
npm run content:check
```

生成命令更新轻量索引；检查命令只比较和验证，不修改文件，适合 CI。

## XSS 边界不能因为折叠改变

Markdown 允许链接、代码和部分 HTML。无论预览还是完整正文，都必须经过同一渲染与清理函数。不要在展开分支里直接使用未经清理的 `v-html`。

代码复制使用渲染区事件委托，按钮从已清理 HTML 中识别；文章正文不能注册任意脚本或内联事件。

## 交互验收清单

- 普通文章没有多余展开按钮；
- 长文首次只出现摘要内容；
- 完整正文点击后才进入 DOM；
- 展开按钮至少 44px 并可键盘操作；
- `aria-expanded` 与真实状态一致；
- 展开后目录增加完整章节；
- 收起后焦点和视口位置稳定；
- 代码复制在两种状态都可用；
- 移动端没有横向滚动；
- reduced-motion 不影响内容可达性；
- 无 JavaScript 时仍有可恢复提示或预渲染策略。

## 最终判断

长文章的问题往往不是“浏览器能不能渲染”，而是信息是否仍然可理解。按需展开是技术手段，内容拆分才是长期方向。

工程化博客应该同时管理三件事：内容质量、构建一致性和阅读成本。任何一项缺失，文章数量增加都会变成新的技术债务。
