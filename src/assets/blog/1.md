> 本文是 2026 年对 2024 年关键 Web 性能变化的回看。目的不是追一项新指标，而是留下以后排查“按钮点了但页面像没反应”时可以复用的方法。

2024 年 3 月，Interaction to Next Paint（INP）正式替代 First Input Delay（FID）成为 Core Web Vitals 指标。FID 只观察首次交互开始前的等待时间，INP 则关注页面生命周期内的多次交互，并测量从输入发生到下一帧真正呈现之间的完整延迟。

## 为什么这个变化值得记住

一个按钮可以在 20ms 内进入事件回调，却在 600ms 后才让用户看到结果。FID 可能认为它响应很快，INP 会把事件处理、样式计算、布局和绘制的时间一起算进去。

因此，INP 更接近用户真正感知到的问题：

- 点击筛选后，列表迟迟不更新；
- 输入搜索词时，字符出现得断断续续；
- 展开卡片时，主线程先做大量计算；
- 移动端连续操作后，某一次交互突然卡顿。

经验阈值可以记成三档：不高于 200ms 为良好，200–500ms 需要改进，高于 500ms 较差。不要为了单次实验室成绩优化，应以真实用户数据的第 75 百分位判断。

## 一次交互由三段组成

```text
输入发生
  → Input delay：主线程什么时候有空处理
  → Processing duration：事件回调执行多久
  → Presentation delay：浏览器多久完成布局、绘制并显示下一帧
```

这三段对应完全不同的修复方向。

### 输入延迟高

通常说明主线程正在执行别的长任务。先检查初始化脚本、第三方 SDK、大型 JSON 解析和一次性组件挂载。修复方法不是给按钮加 loading，而是把无关工作延迟执行或拆成小任务。

### 事件处理时间高

检查回调里是否同步筛选大量数据、深拷贝对象、连续触发响应式更新。Vue 项目中可以先把计算收敛到 `computed`，再确认是否真的需要在每次输入时处理完整数据集。

### 呈现延迟高

重点检查大面积 DOM 更新、强制同步布局和复杂视觉效果。读写布局应分组，动画优先使用 `transform` 与 `opacity`，长列表应分页或虚拟化。

## 在项目里如何观察

```ts
import { onINP } from 'web-vitals'

onINP((metric) => {
  // 生产环境只上报指标和分级，不上传输入内容或 DOM 文本
  reportPerformance({
    name: metric.name,
    value: Math.round(metric.value),
    rating: metric.rating,
  })
})
```

本地 DevTools 适合定位原因，真实用户监控适合判断影响范围。两者不能互相替代：开发机跑得快，不代表低端手机没有长任务；单次 Lighthouse 通过，也不代表复杂操作后的尾部延迟稳定。

## 可复用的排查顺序

1. 先复现具体交互，不从整页性能分数开始。
2. 在 Performance 面板标记输入到下一帧的完整区间。
3. 判断瓶颈属于输入等待、回调执行还是浏览器呈现。
4. 找到大于 50ms 的主线程任务并继续向下定位。
5. 只做与瓶颈对应的修改，再重复同一操作验证。
6. 检查键盘、触摸与 reduced-motion 场景，避免只优化鼠标路径。

## 不要用这些方式“优化”

- 把真实操作延迟藏在更长的动画后面；
- 为降低事件次数而让输入明显变钝；
- 只测首次点击，忽略长时间使用后的交互；
- 上传用户输入、元素文本等不必要的数据；
- 看到 INP 高就重写框架，而不先定位是哪一段耗时。

INP 最重要的价值，是迫使性能优化回到用户动作本身。以后遇到“功能实现了，但就是感觉慢”，先画出这三段时间，再决定改代码的哪一层。
